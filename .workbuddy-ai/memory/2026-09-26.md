## v14: overlapping exchange + real parallax inside the samples
- Client: leaving animation too long and sequential; combine — one leaves by reversing, the other swipes in. And the sample animations are too simple; want real parallax.
- Root cause of the dead beat: the cycle incremented an index, so leave ran fully (1.74s) before enter began. Replaced with a **continuous stage timeline**: `x = ((s - i + ENTER) % n + n) % n - ENTER` where `s = ((now-t0)/CYCLE) % n`. Two panels occupy the same window by construction.
  - x ∈ [-0.19, 0): swipe in from the left (x -700, z -150, s .94, ry .34, op 0→1, blur 7→0, easeOut)
  - x ∈ [0, 0.81]: hold at z +180, no filter
  - x ∈ (0.81, 1]: reverse out to the right (x 300, z -820, s .6, ry -.26, op→0, blur→9, easeIn)
  - CYCLE 5200ms.
- Measured over 52 samples @120ms: **longest gap with nothing visible = 0ms**; longest window with two panels visible = **840ms**.
- Real parallax: scene publishes `--mp` (0→1 across the hold) on the live `.mini-page`; CSS consumes it in `calc()`. `.plate::before` carries the image layer (so it never fights the entrance animations on the element itself). Rates: hero plates -140px, plate rows three rates incl. sideways, copy columns +86px opposite, Lumen gallery -170px.
- Verified: 13 distinct plate transforms / 14 samples, hero plate -90→-118px while the page scrolled -840→-1242px, 60fps, 0 clipped, RM3,359, 0 errors.
- Lesson: **never put backticks inside `node -e "..."` from bash** — bash command-substitutes them and silently deletes the content. Use the Edit tool for docs instead.

## v25: fixed "starts at the bottom then jumps to the top", and shortened the travel
- Client reported the framed page starting at the bottom and restarting from the top. **Cause: only the live panel was being driven.** A panel that is not live keeps whatever scroll position it ended on last cycle — and it is *visible during the swipe-in* (x from -ENTER to 0) before it becomes live. So the visitor saw it parked at the bottom, then it snapped to the top the moment liveIndex picked it up. Nothing was ever wrong with the scroll maths; the bug was in which panels got driven.
- Fix: drive **every** panel each frame, with progress `0` for anything that is not live, so a panel is always at the top before it can be seen. Guarded with a `lastY` map so a frame is only written when the value actually changes (4 frames x 60fps of redundant `scrollTo` was wasted work).
- Also capped the travel: `TRAVEL = 640px` instead of scrolling the entire document, and `CYCLE = 3800ms` so the scroll lasts `3800 x (1 - 0.19) ≈ 3.1s`. Scrolling a 6000px page in 3s was a blur, not a look at the site.
- Verified: max scrollY 604 (was the full document height), **0 of 24 samples had a non-live panel parked below the top**, cycle advancing normally, zero console errors.
- Lesson: when a value is driven only for the "active" item, ask what the *inactive* items are still showing. An element can be on screen before it becomes active.

## v30: game-feel "juice" pass on the exchange
- Client: the animation is too rigid, and asked about the graph games use for juice. That graph is the **easing curve** (Disney slow-in/slow-out, formalised as Robert Penner's tween functions). Reference talks: "Juice it or lose it" (Jonasson & Purho, GDC 2012) and "The Art of Screenshake" (Nijman, GDC 2013). Showed the curves inline as an SVG chart (linear vs easeOutCubic vs easeOutBack vs easeInBack).
- Why it read rigid: plain cubic eases, so a panel arrived and stopped dead, identically every cycle.
- Added an easing kit in `scene.js`: `easeOutCubic`, `easeInCubic`, `easeOutBack(t,k)`, `easeInBack(t,k)`, `settle(t)` (damped oscillation, 0 at t=0 so it can be added without a seam), `overshoot(t) = sin(π·t^1.6)` (zero at both ends, peaking ~two thirds through).
- Applied: **entry** keeps x/z on a plain cubic but scale gets an explicit overshoot envelope and yaw uses `easeOutBack`; **exit** adds a wind-up (`sin` bump, 18-28px the wrong way) on top of `easeInBack`; **hold** gets a damped settle on z, scale and yaw for the first third, so it lands rather than stops. Opacity runs ahead of movement in both directions.
- **Per-cycle variation:** `seed = Math.random()` rerolled each cycle modulates the overshoot and the wind-up, so no two exchanges are identical. This is the cheapest juice lever and the one that most stops it feeling mechanical.
- Measured: scale overshoot went from **0.48% → 2.8%** (rakan peak 1.0292, morsel 1.0271), wind-up registers over ~5 sampled frames, 60fps, zero console errors.
- Lesson: an easing can be mathematically present and visually invisible. Measure the *peak deviation from the target*, not the presence of the curve. First attempt produced 1.0048 and I had to raise it deliberately.

## v49: the slope was backwards AND the camera was fighting it
- Client: "NOPE YOU GOT IT WRONG, I dont mind some overlap, the blurriness of the minisites help. what i want is the direction of the slope. right now its slope outward (from our 3d perspective, the left site of the minisite is closer to the viewer currently, i want the right side to be closer so its sloped inward). plus its too much to the right … in smaller viewport you can barely see the minisite"
- **Two mistakes of mine, and a third root cause I had not suspected.**
- **Mistake 1 — I "fixed" the overlap the client never asked me to fix.** In v48 I read "something feels off" as the panel crossing the headline and moved the stage to a fixed `x = 880`. The client then had to tell me they *like* the overlap ("the blurriness of the minisites help") and that the panel was now invisible on a 1080 viewport. **Lesson: when a client describes a symptom vaguely and then gives a specific instruction, act on the instruction and ask about the symptom — do not invent a third fix and ship it.** The overlap was never the complaint.
- **Mistake 2 — I had the slope sign backwards and documented the wrong one.** v48's README confidently said "positive `ry` is the one you want". It was the opposite. The client's description is the ground truth: left side closer = sloping outward; they want right side closer = sloping inward.
- **Root cause 3, which explains why my measurements kept contradicting each other:** `camera.lookAt(group.position.x * 0.55)` **yawed the camera toward the panel**. A yawed camera views the panel off-axis, and an off-axis flat plane projects as a trapezoid — so the camera was contributing a slope of its own, on top of `ry`, and the size of that contribution changed with the viewport because `group.x` is aspect-dependent. At some widths the two slopes cancelled, at others they compounded. **That is why the slope genuinely appeared to flip depending on window size, and why two "decisive" measurements disagreed.** Changed to `camera.lookAt(0, 0, 0)`, which leaves `ry` as the only thing that can tilt the panel.
- **Mistake 4 — a fixed world x cannot work.** `group.position.x` was an absolute number, but the camera has a fixed fov, so a narrower viewport sees a narrower slice of the world and the same x walks off the right edge. At 1080 the panel was a sliver. Replaced with `stageX()`, a fraction (0.44) of the visible half-width at the panel's depth, recomputed in the resize handler. Panel now sits at 47.9% / 51.4% / 54.6% left across 1080 / 1440 / 1920.
- **The measurement lesson, which cost the most time:** I misread the slope direction **three separate times** from downscaled screenshots at small angles (-0.1, -0.12, -0.18 all render a ~3–15% edge difference, well inside the error of eyeballing a 0.75-scaled image). Only the extreme test settled it: `ry: -1.2` renders the right edge at **367px vs the left at 247px**. Also: a probe reading `matrix3d` gave a confident, plausible, and *wrong* answer, and a probe looking for a CSS `perspective` found none anywhere — CSS3DRenderer bakes the projection into the matrices, so there is no perspective property to find. **At small magnitudes, stop looking and set an absurd value.**
- Final values, all negative: `SWIPE -0.34`, `LIVE -0.18`, `BACK -0.28`, `PARK -0.32`.

## v50: the panel had a fixed world size, so it ballooned on small screens
- Client: "its too big now making it looks unbalanced … slope it further … make it half as big"
- **The size bug was the same class of mistake as the position bug I had just fixed, and I only fixed half of it.** In v49 I made `group.position.x` aspect-relative because a fixed world x walks off screen. I did not notice that `.panel` is also a fixed world size (432×270), so as the viewport narrows the visible world shrinks while the panel does not — it *grows* as a share of the screen. At 1080 it covered about half the width and the hero read as unbalanced. **Position and size were both fixed-world values; I only converted one.**
- Fix: `stageScale()` holds the panel at `REF_FRACTION = 0.3` of the viewport, applied in `place()` as a multiplier on each state's own scale. Verified: ~32% at 1080, 1440 and 1920 (was 49% / 42% / 36%).
- **Applied in `place()`, not to the group.** Scaling the group would also scale the state z offsets, changing the perspective as the panel resizes. Scaling the object leaves the depth relationship alone.
- Both `stageX()` and `stageScale()` are called from the resize handler. Missing that would let the panel drift and resize as the window changes.
- Slope steepened from `-0.18` to `-0.30` (`SWIPE -0.52`, `BACK -0.44`, `PARK -0.5`).
- **Pattern worth naming, because it has now cost three rounds on this one element:** every value in the hero scene was authored as a fixed world number, and a perspective camera makes fixed world numbers wrong the moment the viewport changes. When touching this scene, ask of every constant: *is this a world value or a screen value?* Anything the client perceives as "size" or "position on screen" must be derived from `host.clientWidth / host.clientHeight`, not hardcoded.

## v51: constant physical size, and the trap of the constant fraction
- Client: "its still too big in widescreen while tiny in smaller viewport. what i mean steeper slope, i mean a lot steeper. it should look like a wall in an alley"

## v56: killed the "juice" — the client was right, it was seasickness
- Client: "i hate the bouncy sway. it feels unstable like im at the open seas."
- **This was all my own doing, and I had reasoned my way into it.** Back in the game-feel round I added a "juice kit": `easeOutBack` overshoot on entry, `easeInBack` wind-up on exit, a damped `settle()` oscillation, an `overshoot` envelope, and a per-cycle random `seed` so "no two exchanges are identical". The theory — overshoot reads as weight — is real, but it was calibrated for a small panel.
- **What it actually did at this size, per cycle:**
  - HOLD: `z` wobble of **±46 units** on a panel sitting at z=180 — a 25% depth pulse, i.e. the panel surging toward and away from the viewer. Plus a ±6 vertical bob, a scale pulse and a yaw wobble, all for the first third of the hold.
  - ENTER: z overshoot of 34, scale overshoot, yaw via `easeOutBack` with `k` randomised per cycle.
  - EXIT: a wind-up that pulled the panel the wrong way first.
  - Plus pointer parallax at 130 / 50 / 90, which is ~7.4° of camera yaw at full deflection — the whole scene pitching when the mouse moved.
- **Removed all of it.** Entry and exit now use one plain cubic each; the hold is `{ ...LIVE }` and nothing else. The four helpers and the seed are **deleted, not disabled**, so reintroducing overshoot is a deliberate act. Pointer parallax reduced to 44 / 18 / 40 with faster damping, with a note that setting it to 0 makes the scene fully static if it still reads as swaying.
- **Verified objectively rather than by eye:** sampled the live panel's `matrix3d` across a full hold window — **yaw drift 0.0000, scale drift 0.0000, depth drift 0.0000, height drift 0.0000.**
- **Two measurement traps hit while verifying, both of which produced confident wrong readings:**
  1. `--virtual-time-budget` advances `setTimeout` far faster than it produces frames, so a timer-based probe reported the scene as frozen on `fern@53` for 15 straight samples. It is not frozen — the probe cannot see rAF advance.
  2. Two captures at 9000ms and 16000ms came back **byte-identical** (340753 bytes each), which also looks like a freeze. Same artifact. Confirmed pre-existing: every earlier capture in this session showed "Fern & Fable" regardless of budget, including before this change.
- **Lesson recorded in the README:** do not conclude the carousel is stuck from a headless capture. And more broadly — the "juice" was tuned on theory and never re-checked after the panel grew to 9:16 at 70% of the viewport. Effects calibrated at one size must be re-verified at another.

## v57: aligned the panel to the content column — and a silent total failure
- Client: two annotated screenshots with the content column's edges drawn on — "FOR WIDE SCREEN, THIS FEELS WRONG" / "FOR SMALL SCREEN THIS FEELS WRONG", then "iM OK WITH THE NUMBER OUTSIDE THE RED LINE, BUT THE HERO SECTION SHOULD BE INSIDE".
- **The diagnosis: six attempts had positioned the panel relative to the WINDOW, so it had no relationship to the page's own grid.** It overflowed the `.wrap` column on a wide screen and fell short of it on a narrow one — the two things the red lines marked. Reversing the geometry fixed both at once.
- `stageX()` now derives from the column: `.wrap` is max-width 1240 with 32px padding, centred, so its right edge is `(1240/2) - 32 = 588` from the viewport centre (`CONTENT_RIGHT`), or `viewportWidth/2 - 32` below 1240. The panel's projected half-width is subtracted from that.
- **`PANEL_SPREAD = 1.9` is empirical.** A Y-rotated panel's footprint is far wider than `W * cos(yaw)` because the top and bottom edges slope and the corners swing out. First attempt used the naive `cos` estimate and was still **47–65px outside** the column at every width. Measured the real ratio and applied it. Documented as "re-measure, do not re-derive".
- Verified inside the column at 1080 / 1300 / 1440 / 1920 / 2400 / 3440, slack 22–65px. The folio stays outside on the left, which the client confirmed is wanted.
- **A silent, total failure I caused and then had to hunt.** After the first edit the hero went completely dead — no live panel, no `.scene.ready`. Cause: **`PANEL_W` had never been declared.** An earlier edit dropped the declaration when the size target moved from width to height, and nothing referenced it until `stageX()` did. `const` is not hoisted, so it is a **temporal dead zone error**.
  - **`vite build` passes on this.** Vite cannot see a TDZ error, so the build reports success on a dead page.
  - **The symptom is silent.** `paint()` throws on its first call, so `host.classList.add("ready")` never runs and the rAF loop never starts. No error in the DOM, just an empty hero.
  - What found it: injecting a `window.onerror` + `unhandledrejection` listener into `<head>` **before** the module runs, on a copy of the built page. It reported `REJ PANEL_W is not defined`. An `unhandledrejection` listener is required — the module is an async IIFE, so the throw surfaces as a rejected promise, not a classic error.
  - **Rule now in the README: if the hero goes blank after touching `scene.js`, attach that listener first.** I had earlier mistaken the same blank hero for a *paint-timing* artifact and waited 40s across several captures. It was a dead module. **A blank hero has two very different causes and I assumed the benign one for several rounds.**

## v58: section 02 resolves as you scroll, with a particle burst
- Client: "in section 2 lets add some animation to add juice… maybe its started both bad, but as the user scroll we add in the animation that improve the second version… in my head i can see a particle effect used. lets try it"
- **Both miniatures in each card now start in the "before" state** — dimmed to 0.46, muted red rule, `blur(2.5px) saturate(0.35)`, scaled to 0.985, and the "after" button rendered as the dead one. When the card scrolls into view the second one **resolves**: dim lifts, rule goes to the card's own hue, content sharpens, the dead button becomes the live accent button, and a 14-spark burst fires out of it. The improvement is watched rather than read.
- **`.pending` is added from JS, never in the markup** — a failed script leaves every card resolved rather than permanently dimmed. Same rule as `.reveal`.
- **The resolve waits two `requestAnimationFrame`s** before removing `.pending`, so the pending state is painted first and the transition actually runs instead of collapsing into one style recalculation.
- **Caught a gap by looking:** the phone card's miniature is a `.phone`, not a `.win`, so the first pass left that one card resolving from a state that had never been dimmed. Both selectors are needed.
- Sparks use `var(--hue, var(--accent))` so each card bursts in its own colour — the four read as four separate things resolving rather than one repeated effect.
- Under `prefers-reduced-motion` `main.js` skips adding `.pending` entirely rather than relying on the CSS, and the sparks are `display: none`.
- **Verification notes, both non-obvious:**
  - The pending state lasts about one frame after the scroll, and **CSS transitions do not advance under `--virtual-time-budget`** — a `getComputedStyle` read returned a frozen mid-transition value (opacity 0.898, blur 0.47px) that was identical before and after adding `.pending`. To photograph the unresolved state you must inject `transition: none !important` and add the class by hand.
  - Sparks are removed after 1.1s, so counting them needs to happen **within ~500ms** of the scroll. At 2.6s the count was 0 and looked like the burst had never fired. Confirmed at 500ms: 14 sparks, `spark-out`, correct hue.

## v59: the section-02 trigger, and a rootMargin that stopped firing entirely
- Client: "i think the trigger is too early, by the time i can see the section, all the animation has happened"
- Cause: `rootMargin: "0px 0px -18%"` fires the moment a card clips the bottom edge — ~82% of the viewport — so the whole 0.55s played out below the fold.
- **Raising it to `-52%` stopped it firing AT ALL.** Pending stayed at 4 across scroll positions from 85% down to 30%. No JS errors, the block was in the built bundle, `.pending` was being applied. A large negative `rootMargin` percentage behaves unpredictably in this nested context and I could not pin down why.
- **Replaced it with an explicit position check** — a passive scroll listener comparing `card.getBoundingClientRect().top` against `innerHeight * TRIGGER_AT` (0.55). Plain arithmetic, says what it means, trivially tunable, and verifiable. Verified: nothing fires at 80% or 65%, two cards fire at 50%, stable after.
- **Also fixed a silent gap:** the burst selector was `card.querySelector(".win.good")`, which returns **null** for the phone card (its miniature is `.phone.good`). That card had been resolving correctly but never firing particles. Now `.win.good, .phone.good`.
- **Verification lesson, third time this session:** the iframe harness is unreliable for `IntersectionObserver` (the implicit root resolves against the top-level viewport, and percentage rootMargins behave oddly through the frame). **When a scroll-driven behaviour has to be verified, prefer an explicit position check in the code** — not because it is better code, but because it is the only version I can actually test in this environment.

## v60: one bug, two symptoms — the scheduled resolve re-queued itself
- Client: "1 and 2 is fine but 3 and 4 timing is weird (too late, and the particle effect loops)"
- **Both symptoms came from one mistake in the code I had just written.** The resolve was scheduled inside a `setTimeout` (to let the pending state paint), which left the card still carrying `.pending` for the length of the delay. The scroll guard was `if (!card.classList.contains("pending")) return;` — so **every scroll event during that window re-queued the same card**.
  - Each re-queue scheduled **another burst** → looping particles.
  - Each re-queue incremented a `queue` counter that was **never reset**, and the delay was `queue * 160` → each successive card waited longer than the last. Cards 1 and 2 fired early with small delays and looked fine; 3 and 4 had accumulated a large counter by the time they crossed the line, so they arrived late.
- **The client's report was precise enough to find it directly** — "1 and 2 fine, 3 and 4 late, and it loops" describes a monotonically growing delay plus repeat firing, which is exactly what a never-reset counter and a stale guard produce. Worth noting: a bug report that distinguishes which instances are fine is far more useful than "it's broken".
- Fix: remove `.pending` **synchronously** in the same tick, so the guard holds immediately. Stagger only the burst (`i * 130`), and derive `i` per tick rather than from a running counter.
- **Verified by reproducing the trigger for the bug:** fired **12 scroll events per step** while stepping down the page, then counted sparks. Exactly **28 = 2 bursts of 14** for two cards, zero after. Before the fix the same probe showed the loop.
- Also confirmed all four cards resolve, including the phone card that had been silently getting no burst at all (see v59).

## v61: same trigger fix for the quote builder
- Client: "can u do something similar for the timing of the build your own quote? its triggering too early right now"
- Same root cause as v59: `rootMargin: "100% 0px -15% 0px"` fired when the builder's top reached **85%** of the viewport — the instant it clipped the bottom edge — so the defaults landed and the receipt filled before the visitor had scrolled the builder into view.
- Replaced with the same explicit position check: `wizard.getBoundingClientRect().top <= innerHeight * 0.55`. Verified: **RM0 at 90 / 80 / 70 / 60%, RM3,459 at 50%**, stable after.
- **The full-viewport margin had a real purpose and the position check covers it for free:** it existed so a deep link (or the skip link) that opens the page *below* the builder would still fill it. With an explicit check, such a builder has a **negative** top, which is already past the line, so it fires on the first call. Worth remembering — the "clever" rootMargin was solving a problem a comparison solves naturally.
- `runDefaults()` is idempotent, so a scroll listener calling it repeatedly is harmless. Verified with 10 synthetic scroll events per step, which is also what would have exposed the v60 re-queue bug had it been present here.
- **Both scroll triggers on the page now use the same pattern** (`TRIGGER_AT`, a passive scroll listener, an idempotent action). If a third is added, follow it — and prefer it over `IntersectionObserver` regardless, because it is the only form that can be verified in the iframe harness.

```bash
gh api -X POST repos/rajahafify/hfz-digital-advisory/pages -f build_type=workflow
```

Do this *before* the first push, not after the first failure.

**Sequence that worked:**
```bash
gh repo create hfz-digital-advisory --public --source=. --remote=origin --description "..."
git push -u origin main
gh api -X POST repos/rajahafify/hfz-digital-advisory/pages -f build_type=workflow
```
Note `gh repo create --source=.` adds the remote but does not push; `--push` would have done both. Pushing separately made the failure modes easier to read.
